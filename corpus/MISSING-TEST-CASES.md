# Missing Test Cases — file fixtures

Six production corpus files were removed because we do not own them and cannot
redistribute them without a licence (real photographs, a "calibre" demo
document, a patent-application sample, etc.). Every remaining corpus file is now
100% synthetic and generated by
[`scripts/generate-corpus.ts`](../scripts/generate-corpus.ts).

This document tracks the adapter coverage that left with those files and how to
restore each one with a **license-free, self-generated** fixture. Unless noted,
"how to restore" means adding a generator to `scripts/generate-corpus.ts` so the
fixture is reproducible from bytes we author.

## Removed files → lost coverage → replacement plan

| Removed file | Format | Coverage lost (manifest `features`) | License-free replacement | Effort |
|---|---|---|---|---|
| `blank.pdf` | PDF | `empty_page` — rendering a valid page with **no content stream** | Emit a 1-page PDF whose `/Contents` stream is empty (or omit `/Contents`). Pure string template, same shape as the existing `simple.pdf`. | **Trivial** |
| `TIFF_1MB.tiff` | Image | `tiff_decode` + `large` — decode/memory path for a large (~1 MB) single-page raster | Extend the existing `buildMultipageTiff` helper to emit one large single page (e.g. 600×600 RGB, 8-bit, uncompressed ≈ 1 MB) filled with a procedural gradient/noise pattern. | **Low** |
| `chef-with-trumpet.heic` | Image | `heic_decode` + `large` + `iphone_photo` — the **only** exercise of the HEIC path (`heic2any`) | HEIC needs a real encoder, so we can't hand-write bytes. Options: (a) generate at build time with `libheif`/`ffmpeg` if present, gated behind a capability check; (b) commit one small **CC0/public-domain** HEIC and document its provenance; (c) transcode a generated PNG → HEIC in a pre-test step. | **High** ⚠️ |
| `headers-images.docx` | DOCX | `headers` + `images` (embedded raster) + `table_render` + `multipage` | Extend `createDocx` to add `word/header1.xml` + relationships, embed a generated PNG (reuse the `minimal.png` bytes) via `word/media/`, and force a page break (`<w:br w:type="page"/>`). | **Medium** |
| `headings-lists-columns.docx` | DOCX | `headings` + `lists` + `columns` + `image_alt_text` + `table_render` | Synthesize a DOCX with `<w:pStyle w:val="Heading1..3">` paragraphs, a `word/numbering.xml` part for bulleted + numbered lists, a `<w:sectPr>` with `<w:cols w:num="2">`, and a drawing whose `<wp:docPr descr="...">` carries alt text. | **Medium** |
| `rich-formatting.docx` | DOCX | `typography` + `table_render` + `images` + `complex_layout` + `large` | Synthesize a larger multi-page DOCX combining run properties (bold/italic/underline/color/size/font), several tables, and several embedded generated images. Essentially a superset of the two DOCX fixtures above. | **Medium** |

## Coverage still intact after removal

- **PDF:** format detection, single/multi-page text render, 20-page scroll/perf, optional-content layers, annotations (Square/FreeText/Link).
- **DOCX:** format detection, text render, a single 2×2 table.
- **Image:** format detection for JPEG/PNG/GIF/TIFF, single- and multi-page TIFF decode + thumbnails, benign SVG render.
- **Security (malicious/):** unchanged — SVG script/foreignObject/remote-refs, DOCX js-hyperlink/remote-image, zip bomb, zip path-traversal.

## Priority

1. **HEIC fixture (`heic_decode`)** — highest priority: after removal there is **zero** HEIC coverage, and HEIC has a distinct main-thread `heic2any` code path. Needs an encoder-based or CC0 solution.
2. **DOCX images + headers + lists/columns** — the DOCX adapter now only ever sees plain text and one simple table; embedded images, headers/footers, lists, and multi-column layout are all unexercised.
3. **Large-image decode (`TIFF_1MB`)** — restores the large-raster memory/perf path; easy to synthesize.
4. **Blank PDF (`empty_page`)** — trivial; add to the generator in a few lines.

## Adjacent gaps (pre-existing, not caused by this removal)

- **No WebP fixture** although the image adapter claims WebP support.
- **No AVIF** sample and no AVIF detection in the adapter.
- **No PDF-malicious samples** (JS actions, launch/GoToR actions, XFA scripting) — the invariants are enforced in the adapter but unbacked by a corpus fixture. (Already noted in `README.md`.)
